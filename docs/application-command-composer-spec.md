# Техническое задание: application commands в VoiceRoute

## 1. Цель

Привести работу команд приложений в VoiceRoute к модели Discord:

- список команд используется для поиска и выбора поддерживаемой команды;
- выбранная команда добавляется в основное поле ввода;
- аргументы команды редактируются внутри composer;
- команда выполняется только после обычной отправки;
- публичные и приватные ответы отображаются в ленте сообщений;
- ephemeral-ответ виден только инициатору команды.

Текущие отдельные формы выполнения и карточки результата над composer необходимо удалить.

## 2. Термины

- **Command picker** — список доступных команд, появляющийся после ввода `/`.
- **Composer** — основное поле ввода сообщения.
- **Interaction** — структурированный вызов application command.
- **Public response** — ответ приложения, видимый всем участникам канала.
- **Ephemeral response** — ответ приложения, отображаемый в канале только инициатору.
- **Pending response** — временное состояние ожидания ответа приложения.

## 3. Пользовательский сценарий

### 3.1. Открытие списка

При вводе `/` в пустом composer VoiceRoute открывает command picker.

В списке отображаются:

- название команды;
- описание;
- приложение или бот;
- доступность команды пользователю;
- при необходимости — путь подкоманды.

Picker не является формой выполнения команды.

### 3.2. Фильтрация

При дальнейшем вводе, например `/se`, список фильтруется по названию команды.

Поддерживается управление:

- `Arrow Up` и `Arrow Down` — навигация;
- `Tab` или `Enter` — выбрать команду;
- `Escape` — закрыть picker;
- клик — выбрать команду.

### 3.3. Выбор команды

После выбора:

- picker закрывается;
- команда добавляется в основной composer;
- composer остаётся активным;
- interaction ещё не создаётся;
- запрос к invoke API ещё не отправляется.

Команда должна отображаться как выделенный элемент, например:

```text
/search  query: [________________]  private: [Нет]
```

Для команды без аргументов:

```text
/ping
```

Необходимо визуально отличать:

- название команды;
- имена аргументов;
- введённые значения;
- обязательные аргументы;
- текущий активный аргумент.

### 3.4. Редактирование аргументов

Аргументы заполняются внутри composer, а не в отдельной форме.

Поддерживаемые типы:

- `string`;
- `integer`;
- `number`;
- `boolean`;
- `user`;
- `channel`;
- `role`;
- `attachment`, когда тип поддерживается API;
- choices;
- autocomplete;
- подкоманды и группы подкоманд.

Для `user`, `channel`, `role`, `boolean` и choices следует использовать inline-подсказки или выпадающий список.

Обязательные аргументы должны быть заполнены до отправки. Ошибки валидации отображаются рядом с соответствующим аргументом, а не в отдельном модальном окне.

### 3.5. Отправка команды

Команда отправляется тем же способом, что и обычное сообщение:

- Enter;
- кнопка отправки;
- мобильная кнопка отправки.

При отправке composer определяет режим:

- обычный текст — используется Messages API;
- выбранная application command — используется interaction invoke API.

На сервер отправляется структурированный запрос:

```json
{
  "requestId": "uuid",
  "commandId": "command-id",
  "version": "command-version",
  "options": {
    "query": "текст поиска",
    "private": true
  }
}
```

Текстовая строка `/search ...` не должна отправляться через Messages API и не должна разбираться сервером как обычное сообщение.

Повторное нажатие во время отправки не должно создавать второй interaction.

## 4. Отображение вызова в ленте

После отправки в ленте появляется локальное состояние interaction:

```text
Пользователь использовал /search
Бот отвечает…
```

Оно должно находиться в message history, а не над composer.

Локальный элемент связывается с `interactionId`. После ответа pending-состояние заменяется результатом без скачка интерфейса и дублирования.

## 5. Публичный ответ

Публичный interaction response:

- сохраняется сервером как обычное сообщение приложения;
- передаётся через стандартный поток сообщений;
- отображается всем участникам с доступом к каналу;
- содержит attribution вызванной команды;
- поддерживает обычные возможности сообщения, разрешённые протоколом.

Пример отображения:

```text
Иван использовал /search

SixSevenBot
Найдено 5 сообщений…
```

После получения серверного сообщения соответствующий локальный pending-элемент должен быть заменён или дедуплицирован. Два одинаковых сообщения появляться не должны.

## 6. Ephemeral-ответ

Ephemeral response:

- визуально отображается непосредственно в ленте текущего канала;
- виден только инициатору interaction;
- не попадает в общую историю сообщений;
- не передаётся другим участникам через общий SSE/Gateway stream;
- не индексируется поиском;
- не создаёт обычное `community_message`;
- может быть закрыт инициатором;
- содержит отметку «Видно только вам».

Пример:

```text
Иван использовал /whoami

SixSevenBot
Иван
ID: 123
Роль: member

Видно только вам
```

Ephemeral-сообщения могут храниться в отдельном interaction storage и получаться через защищённый status endpoint. Отдельное хранение не должно приводить к отдельному визуальному окну.

## 7. Deferred response

После `DEFERRED_MESSAGE` в ленте сохраняется состояние:

```text
SixSevenBot отвечает…
```

Если defer ephemeral, pending-элемент видит только инициатор. После создания или редактирования original response pending-элемент заменяется итоговым сообщением.

## 8. Ошибки и таймауты

Ошибки interaction отображаются inline в том же месте ленты.

Пример:

```text
SixSevenBot не ответил вовремя.
Повторите команду.
```

Необходимо различать:

- приложение не подтвердило interaction вовремя;
- interaction истёк;
- приложение недоступно;
- команда больше не существует;
- версия команды устарела;
- у пользователя недостаточно прав;
- callback завершился ошибкой;
- потеряно соединение с Gateway или status endpoint.

Ошибка не должна отображаться отдельной карточкой над composer. Для retry создаётся новый `requestId`; старый истёкший interaction повторно не используется.

## 9. Изменения VoiceRoute Web

### 9.1. Удалить

Из текущей реализации необходимо удалить:

- отдельную форму `.vr-slash-arguments`;
- кнопку «Выполнить команду»;
- отдельную карточку `.vr-slash-result`;
- выполнение команды непосредственно при выборе;
- отдельный submit-flow, конкурирующий с основным composer.

### 9.2. Сохранить

Необходимо сохранить:

- загрузку доступных команд;
- фильтрацию command picker;
- клавиатурную навигацию;
- проверку permissions;
- загрузку users, channels и roles для аргументов;
- идемпотентный `requestId`;
- status polling как fallback;
- поддержку Gateway interaction updates.

### 9.3. Добавить

Нужно добавить:

- структурированное состояние выбранной команды в основном composer;
- inline-редактор аргументов;
- единый обработчик отправки;
- локальный слой interaction items внутри message list;
- связывание pending-состояния с `interactionId`;
- дедупликацию локального состояния и публичного серверного сообщения;
- очистку выбранной команды после успешного invoke;
- восстановление draft при неуспешном invoke;
- корректное поведение при переключении каналов.

## 10. Состояние composer

Рекомендуемая модель:

```ts
type ComposerState =
  | {
      mode: 'message';
      text: string;
    }
  | {
      mode: 'application-command';
      command: ApplicationCommand;
      options: Record<string, unknown>;
      focusedOption?: string;
    };
```

Не следует определять выбранную команду исключительно по тексту draft.

Текст `/search` сам по себе не является достаточным идентификатором: разные приложения могут регистрировать команды с одинаковыми именами.

Необходимо хранить как минимум:

- `applicationId`;
- `commandId`;
- `version`;
- `path`;
- `options`.

## 11. Состояние ленты

Лента должна объединять:

- обычные серверные сообщения;
- локальные pending interactions;
- ephemeral interaction messages текущего пользователя;
- interaction errors.

Рекомендуемая модель локального элемента:

```ts
type LocalInteractionItem = {
  interactionId: string;
  requestId: string;
  channelId: string;
  applicationId: string;
  commandName: string;
  invoker: User;
  status: 'sending' | 'pending' | 'completed' | 'expired' | 'failed';
  ephemeral: boolean;
  messages: InteractionMessage[];
  createdAt: string;
};
```

Локальные interaction items должны сортироваться вместе с сообщениями по времени создания.

## 12. Backend VoiceRoute

Существующую базовую модель необходимо сохранить:

- публичный ответ создаёт обычное сообщение;
- ephemeral хранится отдельно;
- ephemeral доступен только инициатору;
- interaction callback использует отдельный token;
- public и ephemeral follow-ups сохраняют выбранную видимость.

Дополнительно следует проверить:

- status endpoint возвращает данные, достаточные для полноценного рендера ephemeral-сообщения;
- возвращаются автор приложения, content, embeds, attachments, components, flags и version;
- доступ к status endpoint невозможен для другого пользователя;
- публичное сообщение содержит `interactionId` для дедупликации;
- lifecycle original response и follow-ups однозначно представлен в API;
- expired и failed состояния содержат машиночитаемый код ошибки.

## 13. `voiceroute.py`

Публичный интерфейс SDK сохраняется:

```python
await context.respond("Публичный ответ")
await context.respond("Приватный ответ", ephemeral=True)
await context.defer(ephemeral=True)
await context.followup("Продолжение", ephemeral=True)
```

SDK должен продолжать отправлять структурированные interaction callbacks.

Дополнительно рекомендуется:

- документировать разницу между public и ephemeral;
- автоматически логировать необработанные application-command exceptions;
- предоставить опциональный error handler;
- при ошибке callback до ACK позволить приложению отправить ephemeral error response;
- не отправлять slash-команды через обычный Messages API.

## 14. Доступность

Новая реализация должна поддерживать:

- полную клавиатурную навигацию;
- screen reader labels для команды и аргументов;
- объявление выбранной команды;
- объявление обязательных и ошибочных аргументов;
- `aria-live` для pending и error-состояний;
- корректный focus после выбора, отправки и ошибки;
- отсутствие focus trap в command picker.

## 15. Мобильное поведение

На мобильных устройствах:

- picker располагается над composer;
- выбранная команда остаётся внутри composer;
- аргументы могут переноситься на несколько строк;
- клавиатура не должна закрываться после выбора команды;
- отправка выполняется основной кнопкой composer;
- ephemeral-ответ появляется в ленте и автоматически прокручивается в видимую область.

## 16. Тестирование

### 16.1. Unit-тесты

Проверить:

- `/` открывает picker;
- ввод фильтрует команды;
- выбор не вызывает interaction API;
- выбор переводит composer в command mode;
- аргументы редактируются inline;
- обязательные аргументы валидируются;
- Enter отправляет выбранную команду один раз;
- обычный текст продолжает использовать Messages API;
- Escape отменяет выбор команды;
- повторное нажатие не создаёт дубликат.

### 16.2. Integration-тесты

Проверить:

- публичный ответ появляется у всех участников;
- ephemeral видит только инициатор;
- другой пользователь не получает ephemeral через API или события;
- pending заменяется публичным сообщением;
- pending заменяется ephemeral-сообщением;
- public response не дублируется;
- timeout отображается inline;
- переключение канала не переносит interaction в другую ленту;
- одинаковые названия команд разных приложений не конфликтуют.

### 16.3. E2E-сценарии

Обязательные сценарии:

1. `/ping` без аргументов.
2. `/search query:<text> private:false`.
3. `/search query:<text> private:true`.
4. `/whoami` с ephemeral-ответом.
5. Команда с обязательным аргументом.
6. Команда с `user`, `channel`, `role` и choice.
7. Deferred public response.
8. Deferred ephemeral response.
9. Просроченный interaction.
10. Бот отключился после invoke.
11. Двойное нажатие отправки.
12. Две команды с одинаковым названием от разных приложений.

## 17. Критерии приёмки

Работа считается завершённой, если:

- выбор команды не выполняет её автоматически;
- interaction API не вызывается до обычной отправки;
- аргументы редактируются внутри основного composer;
- отдельная форма «Выполнить команду» отсутствует;
- отдельная `.vr-slash-result` карточка отсутствует;
- pending отображается внутри ленты;
- публичный ответ отображается как сообщение приложения;
- ephemeral отображается как сообщение в ленте только инициатору;
- ephemeral недоступен другим пользователям;
- public responses не дублируются;
- обычные сообщения работают без регрессий;
- все unit, integration и E2E-проверки проходят.

## 18. Вне рамок задачи

В данную задачу не входят:

- изменение формата регистрации application commands;
- перевод команд на текстовый prefix parser;
- публикация ephemeral в общей истории;
- изменение системы bot permissions;
- изменение Gateway-протокола без выявленной контрактной необходимости;
- редизайн обычных сообщений, не связанных с interactions.
