# ТЗ: исправить выдачу и отображение Gateway intents в VoiceRoute

## Проблема

Developer Portal позволяет выбрать Gateway intents и показывает их включёнными, но
`GET /api/v1/applications/@me` возвращает их только в `requestedIntents`, а
`approvedIntents` остаётся пустым. В результате Gateway отклоняет запуск бота для любого
выбранного privileged intent.

Подтверждённые примеры:

- `voiceStates`;
- `messageContent`.

Библиотека завершает запуск корректной ошибкой:

```text
PrivilegedIntentRequired: privileged Gateway intents were requested but are not approved
by a VoiceRoute operator: messageContent
```

Права роли бота в сообществе и Gateway intents — разные механизмы. Выдача всех прав роли
не должна считаться approval интента и не исправляет проблему.

## Цель

Сделать настройку intents полностью работоспособной: после действий, которые портал
показывает пользователю как успешное включение интента, сервер должен разрешать его при
Gateway Identify либо явно показывать, что privileged intent ещё ожидает одобрения.

Пользователь не должен видеть включённый чекбокс без понятного статуса и доступного
следующего действия, а приложение не должно навсегда оставаться с пустым
`approvedIntents` из-за отсутствия рабочего процесса рассмотрения.

## Требуемое поведение

### Непривилегированные intents

- Сохранённый intent добавляется в `requestedIntents`.
- Он сразу разрешён для Gateway Identify; запись в `approvedIntents` для него не
  требуется.
- Сервер не возвращает ошибку privileged approval для непривилегированного intent.
- Снятие чекбокса запрещает новые события этого intent.

### Privileged intents

- Сохранение чекбокса создаёт или обновляет заявку на одобрение.
- Портал различает состояния `не запрошен`, `ожидает одобрения`, `одобрен`, `отклонён`
  и `отозван`.
- До одобрения интерфейс не называет intent «включённым» или «разрешённым».
- Владелец приложения видит причину отклонения или отзыва и может отправить заявку
  повторно после изменения настроек.
- Оператор может просмотреть заявку и одобрить либо отклонить её через поддерживаемый
  административный API или интерфейс. Наличие только локального CLI недостаточно для
  завершённого production-процесса.
- После одобрения intent появляется в `approvedIntents`, а Gateway Identify с этим
  intent проходит без перезапуска или переустановки приложения.
- После отзыва intent удаляется из `approvedIntents`; активные Gateway-сессии,
  использующие его, закрываются с документированным кодом и понятной причиной.

## API и данные

- Сохранить разделение `requestedIntents` и `approvedIntents`.
- Возвращать владельцу приложения статус каждого privileged intent и, если применимо,
  дату запроса, дату решения и безопасную для владельца причину решения.
- Все операции запроса, одобрения, отклонения и отзыва должны быть идемпотентными.
- Проверять, что одобрять можно только поддерживаемый privileged intent, который
  запрошен этим приложением.
- Записывать в audit log application ID, intent, предыдущее и новое состояние, actor,
  reason и timestamp. Токены и другие секреты в журнал не записывать.
- Изменение approval должно распространяться на все экземпляры Gateway, а не зависеть
  от памяти одного процесса.

## Исправление существующих приложений

- Найти приложения, у которых privileged intents присутствуют в `requestedIntents`, но
  отсутствуют в `approvedIntents` и для них нет заявки со статусом ожидания.
- Создать для них заявки без автоматического одобрения и без потери текущих настроек.
- Отдельно проверить приложение
  `94340da8-b681-4abe-9cd8-691ed7fb94ef`: запросы `voiceStates` и `messageContent` должны
  быть видны оператору и проходить полный цикл рассмотрения.
- После выкладки выполнить production-проверку, что изменение approval читается через
  `GET /api/v1/applications/@me` и применяется Gateway.

## Обработка ошибок

- Если непривилегированный intent неизвестен или недоступен, Gateway возвращает ошибку
  неизвестного/отключённого intent, а не `PrivilegedIntentRequired`.
- Для privileged intent без approval Gateway возвращает стабильный код ошибки и список
  всех отсутствующих approvals.
- Ответ не должен утверждать, что права канала могут заменить approval.
- Повторное подключение с неизменным набором intents не должно создавать новые заявки.

## Проверки и критерии приёмки

1. Непривилегированный `messages`: сохранить, подключиться к Gateway, получить событие.
2. Непривилегированный `interactions`: сохранить, подключиться и обработать команду.
3. Privileged `messageContent`: запросить, увидеть `pending`, одобрить, увидеть его в
   `approvedIntents`, подключиться и получить неотредактированный content сообщения.
4. Privileged `voiceStates`: запросить, одобрить, подключиться и получить voice-state
   события.
5. Запросить одновременно несколько privileged intents: Gateway сообщает все
   отсутствующие approvals; после одобрения всех подключение успешно.
6. Отклонить заявку: портал показывает `rejected` и причину, intent отсутствует в
   `approvedIntents`.
7. Отозвать ранее выданный approval: новые подключения отклоняются, активная сессия
   закрывается согласно контракту.
8. Проверить существующее приложение с `requestedIntents` и пустым
   `approvedIntents`: заявка появляется в очереди и может быть обработана.
9. Проверить несколько серверных экземпляров: решение, принятое на одном экземпляре,
   сразу учитывается остальными.
10. Автотестами покрыть все intents из реестра и отдельно проверить правильность их
    классификации `privileged/non-privileged`.

Исправление принято, когда пункты 1–10 проходят в CI и smoke-проверке production, а
реальный бот с одобренными `messageContent` и `voiceStates` подключается без
`PrivilegedIntentRequired`.

## Вне рамок задачи

- изменение прав ролей и каналов сообщества;
- изменение состава событий каждого intent;
- изменения Python SDK, кроме обновления контракта при необходимости;
- добавление новых intents.
